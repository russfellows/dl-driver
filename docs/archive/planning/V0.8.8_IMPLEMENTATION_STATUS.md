### ❌ Priority 1: Per-Epoch Shuffle (NOT IMPLEMENTED)

**Status:** 🔴 **0% IMPLEMENTED**

**What Was Planned:**
```yaml
reader:
  shuffle: true
  shuffle_per_epoch: true  # NEW - reshuffle with seed+epoch each epoch
  seed: 42
```

**Implementation Requirements (from ROADMAP_V0.8.8.md):**
1. Add `shuffle_per_epoch` config option
2. Wire into s3dlio `LoaderOptions` (shard_rank, shard_world_size)
3. Per-epoch shuffle: `epoch_seed = base_seed + epoch`
4. Match PyTorch `DistributedSampler.set_epoch()` behavior

**Current Reality:**
- ❌ `grep 'shuffle_per_epoch'` returns **ZERO matches** in entire codebase
- ❌ No config option exists
- ❌ Shuffle happens once at workload start, NOT per-epoch
- ❌ s3dlio LoaderOptions not wired with rank info

**Code Evidence:**
```rust
// Current behavior (single shuffle at start):
if shuffle {
    indices.shuffle(&mut rng);  // Only once!
}

for epoch in 0..num_epochs {
    for idx in &indices {  // ❌ Same order every epoch
        load_sample(idx)
    }
}
```

**Impact:**
- Cannot accurately emulate PyTorch/TensorFlow distributed training
- Epochs see samples in same order (unrealistic for convergence)
- Multi-rank tests don't match real distributed data flow

**Recommendation:**
This is the **highest priority missing feature** per ROADMAP. Should be implemented before v0.8.8 release.

### ❌ Priority 2: Sample-Level Sharding (NOT IMPLEMENTED)

**Status:** 🔴 **0% IMPLEMENTED**

**What Was Planned:**
```bash
--shard-level samples  # NEW - shard at sample level (perfect balance)
--shard-level files    # Current default (file-level sharding)
```

**Implementation Requirements:**
1. Add `--shard-level` CLI flag
2. Add `shard_level: samples` config option
3. Build global sample index across all files
4. Shard samples (not files) by rank
5. Handle cross-file reads for perfect balance

**Current Reality:**
- ❌ `grep 'shard_level'` returns **ZERO matches**
- ❌ Only file-level sharding implemented
- ❌ No sample-level index building
- ❌ Cannot guarantee perfect balance with variable file sizes

**Current Limitation:**
```
Dataset: 100 files with variable samples (900, 1100, 1050, ...)
World size: 64 ranks
Current: Each rank gets different number of samples (imbalanced ❌)
Desired: Each rank gets exactly total_samples/64 samples (balanced ✅)
```

**Workaround:**
Users must ensure all files have exactly the same number of samples (`num_samples_per_file` config).

**Impact:**
- Moderate: Most well-structured datasets have equal samples per file
- Critical: Cannot emulate real-world datasets with variable file sizes
- Missing: Cannot match PyTorch `DistributedSampler` behavior exactly

**Recommendation:**
Implement if time permits, otherwise defer to v0.8.9. Lower priority than per-epoch shuffle.

### ⚠️ Bug #8 Verification: INCOMPLETE

**Status:** 🟡 **PARTIAL** - Fixed in code, but not verified with real I/O in distributed mode

**The Issue:**
Bug #8 fix changed latency measurement from `batch_total_time` (includes compute) to `io_time` (pure I/O). This is logically correct, BUT we cannot verify it works because:

1. **Current tests use page cache** → latency = 0µs (data in RAM)
2. **tmpfs storage** → no real disk I/O
3. **Prefetch pipeline** → main thread sees memory access only

**What PHASE2_VERIFICATION_PLAN.md Recommends:**

Create three test phases on real disk (`direct:///mnt/test/`):
- **Phase A**: No prefetch, 10MB files → expect 5-50ms disk latency
- **Phase B**: With prefetch → expect <1ms (prefetched data)
- **Phase C**: With compute → I/O latency same as Phase B, batch time = ~195ms

**Current Status:**
- ✅ Created test configs: `verify_latency_*.yaml`
- ✅ Generated 2,000 files × 20MB = 40GB dataset (later reduced to 1,140 files)
- ✅ Ran tests with single-process mode (worked correctly)
- ❌ **NOT tested in distributed mode with live_stats_tracker**
- ❌ **NOT verified GET latency metrics appear in distributed output**

**Why This Matters:**
Storage GET latency metrics only appear in distributed mode with `live_stats_tracker`. We haven't actually verified the Bug #8 fix works for its intended use case!

**Recommendation:**
Run distributed agent tests with real disk I/O:
```bash
# Terminal 1
./dl_driver_agent --port 50051

# Terminal 2  
./dl_driver_agent --port 50052

# Terminal 3
./dl-driver distributed run \
    --config verify_latency_with_compute.yaml \
    --agents http://localhost:50051,http://localhost:50052 \
    --shard-strategy interleaved
```

Expected output should show:
```
GET Latency: mean=1234µs, p50=1000µs, p95=2500µs
```

If it shows 0µs with direct://, measurement is wrong.  
If it shows 195000µs (includes compute), Bug #8 is not fixed.  
If it shows 1000-5000µs range (pure I/O), Bug #8 is correctly fixed.
