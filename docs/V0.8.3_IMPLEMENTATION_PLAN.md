### 2. `--mlperf` Flag - Make Functional ✅

**Decision:** Actually implement MLPerf compliance reporting, don't leave unused code.

**MLPerf Storage Result Format (from research):**
- Generates `results.json` with structured metrics
- Uses `mlpstorage reports reportgen` command
- Structure includes:
  ```json
  {
    "run_id": "path/to/run",
    "benchmark_type": "training",
    "model": "unet3d",
    "command": "run",
    "num_processes": 4,
    "parameters": {...},
    "system_info": {...},
    "metrics": {
      "samples_per_second": 1234.5,
      "accelerator_utilization": 0.92,
      "total_compute_time": 45.2,
      "total_benchmark_running_time": 49.1,
      ...
    }
  }
  ```

**Key Metrics:**
- Training: `samples_per_second` + `accelerator_utilization (AU%)`
- AU = (total_compute_time / total_benchmark_running_time) × 100
- Minimum AU threshold per workload (e.g., UNet3D requires AU ≥ X%)

**Implementation:**
- Wire up `MlperfMetrics` object (remove `_` prefix, actually use it)
- Implement JSON output format matching MLPerf Storage style
- Add CSV output format
- Export to `--output` file or stdout
- Mark as "[MLPerf Storage Compatible]" in output
- Add experimental warning initially

**Code Changes:**
- `crates/cli/src/main.rs`:
  - Fix `_metrics` → `metrics` (use the object!)
  - Call `metrics.on_batch()` during training
  - Generate `MlperfReport` at end
  - Output JSON/CSV based on `--format` flag
  
- `crates/core/src/mlperf/mod.rs`:
  - Ensure `MlperfMetrics` tracks all needed data
  - Ensure `MlperfReport::from_metrics()` generates correct format
  - Add MLPerf Storage compatible JSON schema

### 3. `generate` Command - Keep and Clarify ✅

**Decision:** Keep it! Useful for separate data generation workflow.

**Clarification:**
- `dl-driver generate --config x.yaml` → Generate data ONLY
- `dl-driver run --config x.yaml` with `workflow.generate_data: false` → Run training on existing data
- `dl-driver run --config x.yaml` with `workflow.generate_data: true` → Generate + train in one pass

**Implementation:**
- No code changes needed
- Update documentation to clarify use cases
- Add examples showing each pattern

**Documentation Changes:**
- `docs/USER_GUIDE.md`: Add "Data Generation Patterns" section
- `docs/CLI_COMMAND_ANALYSIS.md`: Clarify decision (already done)
- Add examples to README.md

---

### 4. `aggregate` Command - REMOVE ✅

**Decision:** Remove entirely. Legacy hack, superseded by shared memory coordination.

**Rationale:**
- Shared memory coordination handles aggregation automatically (zero temp files)
- Distributed agents use gRPC coordination (not file-based)
- File-based pattern was a workaround before Plan A1 implementation
- Keeping it around confuses users

**Implementation:**
- Remove `Commands::Aggregate` enum variant
- Remove aggregate command handler
- Remove from help text
- Update USER_GUIDE.md to remove references
- Add note in Changelog about removal and replacement

**Code Changes:**
- `crates/cli/src/main.rs`:
  - Remove `Aggregate` variant from `Commands` enum (lines ~156-169)
  - Remove aggregate handler from main match statement (line ~324)
  - Remove any aggregate-related functions
